## 1. 目标与边界

本批只处理有实际运行路径或需要明确记录“不适用”的审计项：

1. 每轮输出 `NEW_SOURCES` 审计行，并分别统计内容节点、容器和条件性的排除节点。
2. 核实容器正文下载路径；只有真实存在时实施 N2 纯容器优化。
3. 核实约束词表重建路径；本仓当前没有对应脚本时不得照搬 WorkBuddy 步骤。
4. 核实并约束 `corrections.md` promotion；没有自动 promotion 路径时不得凭空新增。
5. 修正 `--force-full` 帮助和文档的调度者口径。
6. 对齐 N4/C3/N6 文档说明，以及本仓实际 CLI/stderr 行为。

本批不实现自动归档、不读取冲突队列、不改变 `needs_review`、不改变发布报告字段、不写远端页面。所有条件项必须先由代码搜索、调用链和回归测试证明适用或不适用。

## 3. `NEW_SOURCES` 与 DELTA 计数

`check_delta.py` 的每次 plan 输出必须包含一行：

```text
NEW_SOURCES: <count>（<token>=<父token>/<标题>； ...）
```

规则：

- `count` 只统计本轮需要处理的**内容节点**中判为 `new` 的数量，不包括容器。
- `first_run` 是否计入 `count`：不计入 `new`；首次运行仍按 `first_run` 单独报告。
- 条目按 token 字典序升序排列、去重；每项格式为 `token=父token/标题`，父 token 缺失时用 `(空间根)`。
- 零个 `new` 时固定输出：

```text
NEW_SOURCES: 0
```

- `NEW_SOURCES` 行即使解析降级、远端基线缺失或存在 `unknown` 节点也必须输出；不得因为部分失败而省略审计行。
- audit 行只负责披露，不改变 `new`、`changed`、`unknown`、`deleted` 的判定和下载语义。

DELTA 摘要增加或明确以下字段：

- `containers`：当前快照中的容器数量，单独统计。
- `excluded`：仅在准入排除非空时显示。
- `pure_containers`：仅在 N2 被证明适用且实际检测到符合条件的容器时显示。
- 原有 `skip`、`process`、`new`、`changed`、`deleted`、`unknown` 语义不变。

## 4. N2 纯容器优化

N2 只有在以下条件全部成立时才进入实现：

1. 真实调用链存在对 `has_child is True` 容器正文的下载或解析。
2. 该正文不参与候选正文和来源向量。
3. 跳过下载不会改变现有用户可见结果。

若条件成立：

- 快照为容器记录 `char_count`。
- `char_count` 是有效整数且 `< 200` 时，计为 `pure_containers`，不进入 `process`。
- 缺失、非法或 `>= 200` 时照常下载。
- DELTA 仅在字段存在且计数大于零时显示 `pure_containers N`。

若调用链只递归容器、不下载正文：

- 不实现 `char_count` 或纯容器分流。
- 增加回归测试证明容器不会进入正文下载入口。
- 在 wiki-ingest 设计和技能说明中写明 N2 对本仓不适用，而不是保留可误读的“可选优化”承诺。

## 5. N7 约束词表顺序

本批先确认是否存在发布后按 `feishu_sync_tmp/kb_pages/` 或等价 staging 目录重建约束词表的步骤。

当前本仓没有同名 `sync_constraint_data.py`，也没有可执行的重建入口。处理规则：

- 删除或改写文档中“wiki-ingest 的同步约束清单步骤”这类指向不存在实现的承诺。
- 如果审计发现等价实现，必须在该实现中保证：
  1. 先读取真实权威页或已验证的权威投影。
  2. 再重建词表。
  3. 最后才允许清理临时目录。
- 若只有模板说明而无运行路径，本批记录“不适用”，并增加文档一致性测试，防止后续无意恢复不存在步骤的承诺。

## 6. corrections 累积内容

本仓存在 `corrections.md` 模板，但未发现从空模板自动 promotion 的代码路径。

本批必须满足：

- 不新增自动 promotion，除非后续单独有产品需求和远端写入授权。
- 任何生成 `corrections` 候选的路径都不得以空模板替换远端已存在的纠正登记册。
- 如果审计发现现有路径会重建或覆盖，修改为“先读取当前远端权威页，再在当前内容后追加新卡片”。
- 测试固定：已有红线和词表在追加新卡片后不丢失，不能缩小既有约束集合。
- 文档把 `corrections-promote` 标记为未实现，或明确标注它要求的“读取远端后追加”前置条件；不得继续承诺一个不存在的操作。

## 7. 强制全量、文档与诊断

### 7.1 A1 强制全量

`check_delta.py --force-full` 的帮助文本统一为：

```text
调度方显式传 --force-full 时全部判 changed
```

不得声称 `settings.json` 中存在会被 Python 读取的 `forceFullSync` 键。技能说明、参考文档和测试中的同义旧口径一并移除。

### 7.2 N4 / C3 / N6

若本仓存在对应流程，文档必须写清：

- 先执行实际下载规则，再解释 staging 如何形成。
- staging 版本向量允许滞后，滞后不等于内容漂移。
- 实际权威页面、源快照、候选和远端索引的路径及职责分别是什么。
- 使用本仓实际章节和命令，不照搬 WorkBuddy 的步骤编号。

### 7.3 CLI 与 stderr

- 文档命令列以本仓 `store_cli.py` 实际解析器为准，不使用 WorkBuddy 的固定命令数量。
- 若实现对应 dangling token 诊断，必须逐行输出 token，并调整钉住 stderr 的测试。
- 当前没有同名 `_report_dangling` 时，本批只记录不适用，不先造一个无调用者的诊断入口。

## 8. 验收门槛

离线测试和静态检查必须覆盖：

1. `NEW_SOURCES` 的零、单个、多个、排序、去重、首轮和降级场景。
2. `new` 只统计内容节点；容器进入 `containers`，排除节点条件显示在 `excluded`。
3. N2 调用链审计结果唯一：适用则校验 `char_count` 和阈值；不适用则有容器不下载正文的回归测试。
4. N7 不存在的重建步骤未被文档继续承诺；发现等价路径时验证临时清理顺序。
5. corrections 不丢失既有内容；存在 promotion 路径时验证“读远端后追加”。
6. `--force-full` 的帮助、技能文档和测试不再引用 `forceFullSync` 配置键。
7. N4/C3/N6 文档使用本仓真实路径和步骤编号。
8. CLI 文档命令数与解析器一致，stderr 测试只钉住实际存在的输出。
9. 不产生任何远端写入；需要远端证据的项目只允许只读采样。
