# Codex KB-AI 一致性与发布收口设计

> 日期：2026-09-29｜状态：待用户审阅｜批次：4/4
>
> 本文规定前三批完成后的最终一致性检查、跨侧只读验收和真实发布门槛。本文不新增运行行为；它决定哪些旧口径必须消失、哪些远端证据必须一致，以及在什么条件下才允许 Codex 与 WorkBuddy 并发操作同一 KB-AI。

## 1. 目标与边界

第四批只做收口：

1. 统一技能、协议、模板、CLI 帮助、运维文档和测试中的行为描述。
2. 扫描并清除已经被前两批取代的旧口径。
3. 对远端索引、准入页、页面页尾和实际 Markdown 往返做只读验收。
4. 与 WorkBuddy 交换只读证据，确认双方对同一契约的理解一致。
5. 明确定义真实飞书写入和跨侧并发的放行条件。

本批不增加自动 promotion、不恢复冲突队列、不改变内容权威、不更换远端控制页 schema、不自动归档任何目标页。若第四批发现前三批有未实现的产品要求，必须回到对应批次修正；不能只用文档掩盖行为缺口。

## 2. 最终一致性表面

以下表面必须使用同一套术语和字段语义：

| 表面 | 必须反映的最终语义 |
| --- | --- |
| `docs/workbuddy-feishu-knowledge-base-compatibility.md` | 远端索引是同步状态权威；候选正文是内容权威；本地 state 不作跨轮基线；准入默认纳入且可子树排除 |
| `feishu-knowledge-store/SKILL.md` | 唯一发布路径、条件写入、写后回读、`needs_review` 可重试、无冲突队列、无人工优先合并 |
| `wiki-ingest/SKILL.md` | 源快照、候选时间向量、B1 校验、远端来源基线、准入排除、任务局部清理顺序 |
| 候选模板和提取参考 | `source_edit_time_parts` 的顺序、类型、必填性和与 token/revision 的一一对应 |
| CLI 帮助 | 实际参数、退出码、`--force-full` 调度者语义、实际命令集合 |
| lint 和测试 | 索引/页尾 schema、重复逻辑键、页型作用域、无队列依赖、准入门槛、报告字段 |
| 本地运行报告 | 只描述本轮结果；不能被下一轮当作共享 baseline |

## 3. 旧口径清除清单

最终扫描必须证明以下词汇或行为不再作为当前协议出现：

- “人工编辑优先”
- “三方合并”
- “冲突入队”
- “源未变即保留”
- “`queued`”作为正式发布报告字段
- `conflicts`、`third_party_edits` 作为 D1 报告字段
- `merge_protocol`、`sync_knowledge`、`target_state` 作为可执行发布入口
- `delta_state.json` 作为跨轮来源基线
- `forceFullSync` 作为 Python 会读取的配置键
- 不存在的“同步约束清单”或 `corrections-promote` 运行步骤
- WorkBuddy 固定命令数、步骤编号或文件行号被当作本仓事实

允许保留旧词汇的唯一情形：

- 历史变更记录。
- 验证旧行为已退役或旧命令被拒绝的测试。
- 明确标注为“历史/不适用/已取代”的说明。

## 4. 跨侧只读契约矩阵

第四批必须形成一份双方可核对的只读矩阵，至少包含：

| 契约点 | 必须一致 |
| --- | --- |
| 控制页 token 集合 | 双方明确 `{index, lock, admission}`；缺失 admission 与损坏 admission 语义不同 |
| 索引版本 | `schema_version` 和允许字段一致 |
| 来源版本 | `source_revisions` 与 `source_edit_times` 的键集、类型、缺失/null 规则一致 |
| 候选字段 | `source_edit_time_parts` 与 token/revision 的顺序和校验一致 |
| 页尾字段 | 页面写页时保存的来源向量和时间映射一致 |
| 正文权威 | 只有正文内容比较决定 publish/preserve；revision 不能替代比较 |
| 准入 | 未裁定默认纳入；`exclude` 作用于自身和全部后代；`admit` 只撤销排除 |
| 失败状态 | `needs_review` 是可重试的安全状态，不是冲突队列 |
| 报告披露 | 覆盖人工编辑的字段语义和触发条件一致 |
| 删除语义 | 源删除不自动归档；无充分证据不推断删除 |

矩阵中的每一项必须对应：

- 本仓实现或明确不适用说明。
- 离线测试。
- 至少一个只读远端证据或双方确认的契约 fixture。
- 若双方不一致，负责人、待决问题和禁止上线的范围。

## 5. 只读远端验收

前三批离线测试全绿后，才允许执行授权的只读验收：

1. 读取并验证 `AI_KB_INDEX_V1`、`AI_KB_LOCK_V1` 和 `AI_KB_SOURCE_ADMISSION_V1`；不得写入或续租远端锁。
2. 选择稳定的已发布页面，执行候选正文、当前页正文和飞书 Markdown 往返比较。
3. 验证纯排版差异判 `preserve`；实际文字、标点、URL、代码或字面符号变化判 publish。
4. 验证重复运行不会因为相同的远端 revision 或本地状态而跳过正文比较。
5. 验证准入页缺失、空排除、叶子排除、容器子树排除和未来新增后代的行为。
6. 验证来源时间缺失/冲突时 fail-safe 为处理，而不是错误 skip。
7. 验证页面页尾、索引条目和控制文档在只读解析下没有未知字段或 schema 漂移。
8. 保存脱敏验收记录：命令、时间、revision、决策和未验证项；不得保存令牌、正文私密内容或认证信息。

只读验收通过不等于授权写入。真实 publish 必须另行获得用户明确授权，并遵守第六节的发布门。

## 6. 真实发布与并发解除门槛

以下条件必须全部满足：

1. 第一批至第三批的代码、测试和文档收口完成。
2. 第二、三批没有未解决的 P0 或 P1 行为缺口。
3. Feishu store、wiki-ingest、knowledge-loader 及相关插件测试全部通过。
4. 静态旧口径扫描没有未解释的运行时引用。
5. 远端只读验收通过，且 WorkBuddy/Codex 对契约矩阵无未决分歧。
6. 准入门、来源基线、`source_edit_times` 和正文比较在真实只读样例上通过。
7. 用户明确批准真实发布或并发操作。
8. 双方使用同一份调度规则：持远端租约、按当前 revision 条件写入、写后回读、索引更新后回读。

在门槛满足前：

- 不允许 Codex 与 WorkBuddy 同时操作同一 KB-AI。
- 不允许用本地 report、state、cache 或 manifest 恢复远端索引。
- 不允许把 dry-run 结果报告为已发布。
- 不允许把损坏的准入页或损坏索引当作空策略继续尝试；准入页缺失按空排除处理，但必须披露。

## 7. 最终交付物

第四批完成时必须存在：

- 兼容协议的新版本号和双方确认的变更摘要；本仓不得单方面宣称对方已兼容。
- 已更新的技能、模板、CLI 帮助、兼容协议和运维步骤。
- 完整离线测试记录和静态扫描结果。
- 只读远端验收记录。
- 已知差异清单，明确每项为“已解决”“不适用”或“阻断发布”。
- 一份发布门清单，逐项记录负责人、证据和是否满足。

## 8. 验收与失败处理

- 任一旧口径仍被运行时消费者读取：失败，回到所属批次修正。
- 任一契约矩阵项只有文档、没有测试或只读证据：失败。
- 只读验收发现 Codex 与 WorkBuddy 行为不一致：停止发布，更新对应 spec 和 plan 后重验。
- 准入页、索引页或页尾 schema 与预期不同：fail-closed，不降级为空策略。
- 用户未明确授权：只能保留只读结果，不能执行真实 publish。
- 第四批不得通过修改测试预期来掩盖未实现的行为；测试必须反映已验证的共享契约。
